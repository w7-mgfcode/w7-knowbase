Hierarchical RAG

Többszintű visszakeresés: előbb összefoglalók, majd a kiválasztott szakaszok részletes darabjai. Multi-level retrieval: summaries first, then the detailed chunks of the selected sections.

01

ÁttekintésOverview

A Hierarchical RAG több réteget épít: előbb összefoglalók szintjén keres, majd a kiválasztott szakaszokon belül szűkít a részletes darabokra. Így nagy dokumentumokban is megőrzi a kontextust. Hierarchical RAG builds multiple layers: it first searches at the summary level, then narrows to detailed chunks within the selected sections — keeping context intact even in large documents.

A rétegzett index megőrzi a globális kontextust, miközben a végső válasz a pontos, részletes darabokra épül — ez csökkenti a hosszú dokumentumoknál jellemző kontextusvesztést. The layered index preserves global context while the final answer is built from precise, detailed chunks — reducing the context loss typical of long documents.

A metaadat-index irányítja a keresést a releváns kategóriára; a kis levél chunk-okban való precíz egyezés után a rendszer a szülő chunk-ot kéri le a teljes kontextusért. The metadata index routes the search to the relevant category; after precise matching in small leaf chunks the system retrieves the parent chunk for full context.

04

AlapelvekCore Principles

Több granularitási szintMultiple granularities

Legalább két szemcsézettség: kis gyermek-darabok (~100–500 token) a pontos egyezésért, nagy szülő-darabok (~500–2000 token) a kontextusért. At least two granularities: small child chunks (~100–500 tokens) for precise matching, large parent chunks (~500–2000 tokens) for context.

Kicsin keress, nagyon generáljRetrieve on the small, generate on the big

A vektoros keresés a kis gyermek-darabokon fut a precizitásért, de a generáló modell a hozzá tartozó nagy szülő-darabot kapja meg. Vector search runs over the small child chunks for precision, but the generation model receives the larger parent chunk they belong to.

Automatikus összevonásAuto-merging

Ha egy szülő több gyermek-darabja is bekerül a találatok közé, a rendszer összevonja őket, és a szülő-darabbal helyettesíti a töredékeket. When many children of one parent are retrieved, the system collapses them and replaces the fragments with the parent chunk.

Struktúra megőrzéseStructure preservation

A darabolás a dokumentum tényleges szerkezetét (szakaszok, fejezetcímek) követi, nem önkényes, fix méretű vágásokat alkalmaz. Chunking follows the document's actual structure (sections, headings) instead of arbitrary fixed-size cuts.

05

Felhasználási esetekUse Cases

A Hierarchical RAG ott a legerősebb, ahol hosszú, strukturált dokumentumokban egy pontos találatot a környező szakasz kontextusával együtt kell megválaszolni. Hierarchical RAG is strongest where a precise hit in long, structured documents must be answered together with its surrounding section context.

Műszaki kézikönyvekTechnical manuals

Hosszú, fejezetekre tagolt dokumentációk, ahol egy lépés a fejezet egészének kontextusában értelmezendő. Long, chapter-structured documentation where a step is interpreted in the context of the whole chapter.

Jogi szerződésekLegal contracts

Szerződések és jogszabályok, ahol egy záradék jelentése a tágabb szakasztól függ. Contracts and statutes where a clause's meaning depends on the broader section.

Kutatási cikkekResearch papers

Tudományos cikkek, ahol egy eredmény a módszertani szakasz nélkül félreérthető. Research papers where a result is ambiguous without its methodology section.

Megfelelőségi dokumentumokPolicy & compliance docs

Szabályzatok és megfelelőségi anyagok, ahol egy előírás a teljes szakasz hatókörében érvényes. Policy and compliance material where a rule applies within the scope of an entire section.

Pénzügyi beszámolókFinancial filings

Éves jelentések és tőzsdei beadványok, ahol egy számadat a kísérő magyarázattal együtt értelmes. Annual reports and regulatory filings where a figure is meaningful only with its accompanying narrative.

Egy-dokumentumos Q&ASingle-document Q&A

Egyetlen hosszú, tagolt dokumentum mély lekérdezése, ahol a precíz egyezés és a kontextus egyaránt számít. Deep querying of a single long, structured document where both a precise hit and its context matter.

06

Útválasztási stratégiaRouting Strategy

A Hierarchical RAG jó alapértelmezés közepes komplexitású, egyetlen korpuszon végzett visszakereséshez, ha a dokumentumok hosszúak és strukturáltak. Egy útválasztó akkor irányít ide, amikor a Flat RAG túl zajos lenne, de a Graph RAG túlméretezett. Hierarchical RAG is a good default for medium-complexity single-corpus retrieval over long, structured documents. A router sends a query here when Flat RAG would be too noisy, but Graph RAG would be overkill.

A Flat RAG helyettOver Flat RAG

Az útválasztó akkor választja ezt a Flat RAG helyett, ha a dokumentumok hosszúak és tagoltak, így a fix méretű darabolás kontextust veszítene. A router picks this over Flat RAG when documents are long and structured, so fixed-size chunking would lose context.

A Graph RAG helyettOver Graph RAG

A Graph RAG helyett akkor irányít ide, ha nincsenek dokumentumokon átívelő, relációs lekérdezések — egyetlen korpuszon belüli, strukturált keresésről van szó. It routes here over Graph RAG when there are no cross-document relational queries — the task is structured retrieval within a single corpus.

Tárolási rétegStorage layer

Bármelyik megvalósításhoz egy dokumentumtár (docstore) réteggel kiegészített vektoros adatbázis kell: a gyermek-darabok beágyazásai a vektoros indexbe, a szülő-darabok pedig a dokumentumtárba kerülnek, hogy lekérdezéskor a szülő visszakérhető legyen. Any implementation needs a vector store paired with a docstore layer: child-chunk embeddings go into the vector index, while parent chunks live in the doc store so the parent can be retrieved at query time.

Várható eredményekExpected Results

A hierarchikus visszakeresés a Flat RAG-hoz képest javítja a visszakeresés precizitását (kis darabok), miközben nem veszíti el a generálás kontextusát (nagy darabok) — mérsékelt többlet tárhely-költség mellett, mert mindkét granularitás tárolódik. Hierarchical retrieval improves retrieval precision (small chunks) over Flat RAG while not losing generation context (large chunks) — at a modest extra storage cost, since both granularities are stored.

KiértékelésEvaluation

A kiértékelés a RAGAS négy alapmetrikájára épül; a hierarchikus felépítés esetén a kulcsjel a precizitás javulása anélkül, hogy a megalapozottság romlana. Evaluation builds on the four RAGAS core metrics; for a hierarchical setup the key signal is precision improving without faithfulness degrading.

KulcsjelekKey signals

  • Kontextus-precizitás (context precision) javul — kevesebb zaj a kis darabokból.Context precision improves — less noise from the small chunks.
  • Megalapozottság (faithfulness) tartja szintjét — a szülő-kontextus ép marad.Faithfulness holds — the parent context stays intact.
  • Kontextus-visszahívás (context recall) és válasz-relevancia a RAGAS-készlet részeként mérve.Context recall and answer relevancy measured as part of the RAGAS set.

Architektúraspecifikus figyelmeztetésArchitecture-specific concern

KódpéldaCode example

hierarchical_rag_query.py 
# Build a hierarchical index with parent-child chunk relationship.
# LangChain alternative: ParentDocumentRetriever (embed child, return parent).
from llama_index.core import VectorStoreIndex, StorageContext
from llama_index.core.node_parser import HierarchicalNodeParser, get_leaf_nodes
from llama_index.core.retrievers import AutoMergingRetriever
from llama_index.core.storage.docstore import SimpleDocumentStore

# Parse into 3-level hierarchy: 2048 → 512 → 128 tokens
node_parser = HierarchicalNodeParser.from_defaults(
    chunk_sizes=[2048, 512, 128]
)
nodes = node_parser.get_nodes_from_documents(documents)
leaf_nodes = get_leaf_nodes(nodes)

# Store all nodes so parent retrieval works at query time
docstore = SimpleDocumentStore()
docstore.add_documents(nodes)

storage_context = StorageContext.from_defaults(docstore=docstore)
index = VectorStoreIndex(leaf_nodes, storage_context=storage_context)

# AutoMergingRetriever: if >50% of sibling chunks match, return the parent
base_retriever = index.as_retriever(similarity_top_k=6)
retriever = AutoMergingRetriever(
    base_retriever,
    storage_context,
    verbose=False,
)
nodes = retriever.retrieve(question)
