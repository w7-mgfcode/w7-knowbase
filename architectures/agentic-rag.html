Agentic RAG

LLM-ágens vezérli a folyamatot: ő dönt a keresésről, az eszközhívásokról és a leállásról. An LLM agent drives the loop: it decides on retrieval, tool calls, and when to stop.

01

ÁttekintésOverview

Az Agentic RAG egy LLM-ágenst helyez a folyamat középpontjába: az ágens dönti el, mikor keressen, milyen eszközt hívjon, és mikor elég az összegyűjtött kontextus a válaszhoz. Agentic RAG puts an LLM agent at the centre of the loop: the agent decides when to retrieve, which tool to call, and when the gathered context is enough to answer.

Az ágens több lekérdezési kört is futtathat, eszközöket hívhat és közbenső eredményeket értékelhet, így összetett, több lépéses feladatokat is megold — cserébe magasabb késleltetés és költség mellett. The agent can run several retrieval rounds, call tools, and evaluate intermediate results, solving complex multi-step tasks — at the cost of higher latency and spend.

Az ágens iteratív hurkot futtat: tervez, eszközt hív, megfigyeli az eredményeket, majd dönt – folytatja a keresést vagy generál. The agent runs an iterative loop: plans, calls a tool, observes results, then decides – continue retrieval or generate.

04

AlapelvekCore Principles

Az Agentic RAG abban tér el a korábbi mintáktól, hogy a visszakeresés már nem rögzített lépés, hanem az ágens által vezérelt döntés. Az alábbi alapelvek határozzák meg a mintát. Agentic RAG departs from earlier patterns in that retrieval is no longer a fixed step but an agent-driven decision. The principles below define the pattern.

A keresés egy eszközRetrieval is a tool

A rendszer maga dönti el, kell-e keresni, mit és mikor — a visszakeresés egy meghívható eszköz, nem a folyamat kötelező állomása. The system itself decides whether, what and when to retrieve — retrieval is a callable tool, not a mandatory stage of the pipeline.

Ágens-hurokAgent loop

Tervezés → keresés → következtetés → kritika → újrafogalmazás → reflexió, amíg az ágens magabiztos nem lesz, vagy ki nem merül a költségkeret. Plan → retrieve → reason → critique → rewrite → reflect, looping until the agent is confident or the budget is exhausted.

Több lépéses következtetés eszközhasználattalMulti-step reasoning with tools

Az ágens több-lépéses, multi-hop következtetést végez, és közben eszközöket hív: keresőt, kalkulátort, al-visszakeresőket vagy webes keresést. The agent performs multi-step, multi-hop reasoning, calling tools along the way: search, calculators, sub-retrievers or web search.

Önjavítás és többágenses ellenőrzésSelf-correction & multi-agent checks

Sikertelen keresés esetén az ágens újrafogalmazza a lekérdezést; gyakran többágenses felállás működik, ahol szakosodott ágensek ellenőrzik egymást. On a failed retrieval the agent rewrites the query; the setup is often multi-agent, with specialized agents checking each other.

05

Felhasználási esetekUse Cases

Az Agentic RAG ott térül meg, ahol a kérdés egyetlen kereséssel nem válaszolható meg. A 2026-os konszenzus szerint az ágensalapú RAG „a legtöbb éles RAG-rendszert hajtó architektúra”. Agentic RAG pays off where a question cannot be answered with a single retrieval. The 2026 consensus is that agentic RAG is "the architecture driving most production RAG systems".

Multi-hop kutatásMulti-hop research

Több lépéses kutatási kérdések, ahol a válasz több forrás összekapcsolt láncolatából áll össze. Multi-hop research questions where the answer is assembled from a linked chain of several sources.

Kétértelmű lekérdezésekAmbiguous queries

Pontosítást igénylő, homályos kérdések, ahol az ágens visszakérdez vagy szűkíti a keresést. Vague queries needing clarification, where the agent asks back or narrows the search.

DöntéstámogatásDecision support

Jogi, orvosi és pénzügyi döntéstámogatás, ahol több forrás mérlegelése elengedhetetlen. Legal, medical and financial decision support, where weighing several sources is essential.

Vállalati asszisztensekEnterprise assistants

Több eszközt és adatforrást átfogó vállalati asszisztensek egységes felületen. Enterprise assistants spanning multiple tools and data sources behind a single interface.

Deep-research folyamatokDeep-research workflows

Mélykutatási munkafolyamatok, ahol az ágens önállóan tervezi és bővíti a forrásgyűjtést. Deep-research workflows where the agent autonomously plans and expands its source gathering.

Eszközökön átívelő feladatokCross-tool tasks

Keresést, számítást és külső API-kat ötvöző feladatok egyetlen, vezérelt folyamatban. Tasks combining search, computation and external APIs in one orchestrated flow.

06

Útválasztási stratégiaRouting Strategy

Az Agentic RAG gyakran maga az útválasztó: egy LLM vagy ágens kérdésenként dönti el, kihagyja-e a keresést, egyetlen kört futtat, iterál, vagy webes keresést hív. Az Adaptive RAG taxonómiájában ez a legmagasabb komplexitású réteg. Agentic RAG often is the router: an LLM or agent decides per query whether to skip retrieval, do single-shot retrieval, iterate, or call web search. Within the Adaptive RAG taxonomy it is the highest-complexity tier.

Mikor irányít ide az útválasztóWhen the router selects this tier

Egy rendszerszintű útválasztó akkor küldi a kérdést az Agentic RAG-hoz, ha az multi-hop következtetést, eszközhasználatot vagy önjavító keresést igényel — és elkerüli, ha a kérdés egylépéses, ténykereső jellegű (oda a Flat RAG a megfelelő réteg). Mivel ez a legdrágább tier, csak akkor érdemes ide irányítani, ha az olcsóbb minták előreláthatóan elbuknának. A system-level router sends a query to Agentic RAG when it needs multi-hop reasoning, tool use, or self-correcting retrieval — and routes away when the query is single-step and factual (Flat RAG is the right tier there). Because this is the most expensive tier, route here only when the cheaper patterns would predictably fail.

Ajánlott keretrendszerekRecommended Frameworks

Az ágensalapú RAG-ot 2026-ban néhány érett orkesztrációs keretrendszer uralja. A választás a feladat jellegétől függ: állapottartó hurkok, eseményvezérelt folyamatok, szerepalapú többágenses felállás vagy optimalizálható pipeline-ok. Agentic RAG in 2026 is dominated by a handful of mature orchestration frameworks. The choice depends on the task: stateful loops, event-driven flows, role-based multi-agent setups, or optimizable pipelines.

Várható eredményekExpected Results

Az Agentic RAG egy minta, nem egyetlen lemért módszer, ezért a nyereséget feltételesen érdemes kezelni — a többletköltség akkor térül meg, ha a feladat valóban több lépést igényel. Agentic RAG is a pattern, not a single benchmarked method, so gains should be treated conditionally — the extra cost earns its keep only when the task genuinely needs multiple steps.

Mikor térül meg a költségWhen the cost is justified

Az ágensalapú RAG a multi-hop, kétértelmű és magas tétű kérdéseken „termeli ki” a 3–10× tokent és 2–5× késleltetést. Egyszerű, egylépéses kérdéseken a többletköltség nem térül meg — ott egy olcsóbb minta a helyes választás. A fenti számok iparági becslések, nem rögzített tények: az Agentic RAG nem egyetlen benchmarkolt módszer, hanem egy minta, így a tényleges nyereség a feladattól függ. Agentic RAG "earns" its 3–10× tokens and 2–5× latency on multi-hop, ambiguous and high-stakes queries. On simple, single-step questions the extra cost is not recovered — a cheaper pattern is the right choice there. The figures above are industry estimates, not fixed facts: Agentic RAG is a pattern, not a single benchmarked method, so the actual gain depends on the task.

KiértékelésEvaluation

Az ágensalapú RAG kiértékelése három rétegben történik: kérdésenkénti minőség, a teljes ágens-pálya átvizsgálása, és a hosszú távú elcsúszás (drift) figyelése. Evaluating agentic RAG happens in three layers: per-query quality, inspection of the full agent trajectory, and monitoring of long-term drift.

  • Kérdésenkénti RAGAS — context precision, context recall, faithfulness, answer relevancy. Iparági célértékek: faithfulness ≥ 0,9, answer relevancy ≥ 0,85, context precision ≥ 0,8.Per-query RAGAS — context precision, context recall, faithfulness, answer relevancy. Industry targets: faithfulness ≥ 0.9, answer relevancy ≥ 0.85, context precision ≥ 0.8.
  • Pálya-nyomkövetés — Arize Phoenix vagy Langfuse: minden hurok-lépés (terv, eszközhívás, megfigyelés) átvizsgálható, így a hiba pontosan lokalizálható.Trajectory tracing — Arize Phoenix or Langfuse: every loop step (plan, tool call, observation) is inspectable, so failures can be pinpointed.
  • Drift-figyelés — éles környezetben a minőség romlásának folyamatos követése, hogy a regresszió még a felhasználók előtt kiderüljön.Drift monitoring — continuous tracking of quality degradation in production, so regressions surface before users do.

KódpéldaCode example

agentic_rag_graph.py 
# LangGraph agentic RAG — retrieve → grade → generate loop
from langgraph.graph import StateGraph, END
from typing import TypedDict, List

class AgentState(TypedDict):
    question: str
    documents: List[str]
    generation: str
    attempts: int

# Node: retrieve documents from vector store
def retrieve(state: AgentState) -> AgentState:
    docs = vector_store.similarity_search(state["question"], k=4)
    return {**state, "documents": [d.page_content for d in docs]}

# Node: grade document relevance with an LLM judge
def grade_documents(state: AgentState) -> AgentState:
    relevant = [
        doc for doc in state["documents"]
        if grader_chain.invoke({"question": state["question"], "doc": doc})
    ]
    return {**state, "documents": relevant}

# Node: generate answer from graded context
def generate(state: AgentState) -> AgentState:
    answer = rag_chain.invoke({
        "context": "\n\n".join(state["documents"]),
        "question": state["question"],
    })
    return {**state, "generation": answer, "attempts": state["attempts"] + 1}

# Edge: decide whether to retry or finish
def decide(state: AgentState) -> str:
    if not state["documents"] and state["attempts"] < 3:
        return "retrieve"   # no useful docs yet — loop back
    return END

# Build and compile the state graph
graph = StateGraph(AgentState)
graph.add_node("retrieve", retrieve)
graph.add_node("grade", grade_documents)
graph.add_node("generate", generate)
graph.set_entry_point("retrieve")
graph.add_edge("retrieve", "grade")
graph.add_conditional_edges("grade", decide, {"retrieve": "retrieve", END: "generate"})
graph.add_edge("generate", END)
chain = graph.compile()

result = chain.invoke({"question": "What are the deployment steps?", "documents": [], "generation": "", "attempts": 0})
