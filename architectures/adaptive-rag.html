Adaptive RAG

A kérdés nehézségéhez igazított keresési stratégia — olcsó út az egyszerűhöz, mély folyamat az összetetthez. Retrieval strategy matched to query difficulty — a cheap path for simple questions, a deep pipeline for complex ones.

01

ÁttekintésOverview

Az Adaptive RAG először a kérdés nehézségét osztályozza, majd ehhez illeszti a keresési stratégiát: egyszerű kérdésnél olcsó, egyenes utat választ, összetettnél több lépéses, drágább folyamatot. Adaptive RAG first classifies the difficulty of the query, then matches the retrieval strategy to it: a cheap, direct path for simple questions, a multi-step, costlier pipeline for complex ones.

Egy osztályozó előre megbecsüli a kérdés bonyolultságát, és ehhez rendel stratégiát: így a rendszer nem pazarol erőforrást egyszerű kérdésekre, és nem ad alulkutatott választ a nehezekre. A classifier estimates the complexity of the query up front and assigns a strategy — so the system neither wastes resources on easy questions nor under-researches the hard ones.

04

Mikor érdemes használniWhen to use it

ErősségekStrengths

  • Vegyes nehézségű kérdések esetén 40–60%-os költségmegtakarítás.40–60% cost saving when queries vary widely in difficulty.
  • Az egyszerű kérdések rögtön, felesleges retrieval nélkül kapnak választ.Simple questions get instant answers without unnecessary retrieval.
  • Több RAG stratégia egységes, bővíthető keretbe illeszthető.Multiple RAG strategies fit into a single, extensible framework.
  • Átlagos késleltetés csökken, mert az egyszerű útvonal nagyon gyors.Average latency drops because the simple path is very fast.

KihívásokTrade-offs

  • Az osztályozó pontossága meghatározó — hibás besorolás rossz útvonalat aktivál.Classifier accuracy is critical — misclassification triggers the wrong path.
  • Több RAG stratégia karbantartása növeli a rendszer komplexitását.Maintaining multiple RAG strategies increases system complexity.
  • Az osztályozó maga is extra latency- és cost-overhead, ha LLM alapú.The classifier itself adds latency and cost overhead when LLM-based.

Pro tippPro tip

Kezdj egyszerű heurisztikával az osztályozáshoz (kérdéshossz, kulcsszavak), mielőtt LLM-alapú osztályozóra váltanál — sokszor a szabályalapú megközelítés is elegendő pontosságot ad, töredék késleltetéssel. Start with simple heuristics for classification (question length, keywords) before switching to an LLM-based classifier — rule-based approaches often achieve sufficient accuracy at a fraction of the latency.

KódpéldaCode example

adaptive_rag_router.py 
# Complexity levels returned by the classifier
from enum import Enum
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate

class Complexity(str, Enum):
    SIMPLE = "simple"
    MEDIUM = "medium"
    COMPLEX = "complex"

# Lightweight classifier — falls back to LLM when heuristics are uncertain
def classify_query(question: str, llm: ChatOpenAI) -> Complexity:
    prompt = ChatPromptTemplate.from_messages([
        ("system", "Classify the query complexity as 'simple', 'medium', or 'complex'. "
                   "Reply with ONLY the label."),
        ("human", "{question}"),
    ])
    result = (prompt | llm).invoke({"question": question})
    return Complexity(result.content.strip().lower())

# Adaptive router dispatches to the right retrieval strategy
def adaptive_rag(question: str, retriever, llm: ChatOpenAI) -> str:
    complexity = classify_query(question, llm)

    if complexity == Complexity.SIMPLE:
        # No retrieval — LLM answers from parametric knowledge
        return llm.invoke(question).content

    elif complexity == Complexity.MEDIUM:
        # Single-step RAG
        docs = retriever.invoke(question)
        context = "\n\n".join(d.page_content for d in docs)
        return llm.invoke(f"Context:\n{context}\n\nQuestion: {question}").content

    else:
        # Multi-step iterative RAG — refine the query, retrieve again
        refined = llm.invoke(
            f"Decompose into 2–3 sub-questions: {question}"
        ).content
        all_docs = []
        for sub_q in refined.split("\n"):
            all_docs.extend(retriever.invoke(sub_q.strip()))
        context = "\n\n".join(d.page_content for d in all_docs)
        return llm.invoke(f"Context:\n{context}\n\nQuestion: {question}").content
