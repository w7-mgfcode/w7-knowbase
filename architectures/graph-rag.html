Graph RAG

Tudásgráf-alapú visszakeresési architektúra komplex entitás-kapcsolatok feltárására és kontextusban gazdag válaszgenerálásra. Knowledge-graph retrieval architecture for uncovering complex entity relationships and generating context-rich answers.

01

ÁttekintésOverview

A Graph RAG túlmutat a hagyományos vektoros keresésen. Míg a klasszikus RAG dokumentumdarabokat keres szemantikai hasonlóság alapján, a Graph RAG egy strukturált tudásgráfot használ az információk összekapcsolására. Így a rendszer „átléphet” az egymástól független dokumentumok határain. Graph RAG goes beyond traditional vector search. Where classic RAG retrieves document chunks by semantic similarity, Graph RAG uses a structured knowledge graph to interconnect information — letting the system traverse the boundaries between otherwise disconnected documents.

Az architektúra különösen erős a több-lépéses következtetést igénylő kérdéseknél, például: „Hogyan hat az A projekt a B és C csapat együttműködésére?” A gráf élei mentén történő bejárás pontosabb kontextust ad a generáló modellnek. The architecture is especially strong for questions that need multi-hop reasoning, such as: “How does Project A affect collaboration between teams B and C?” Traversing the graph edges gives the generation model more accurate context.

04

AlapelvekCore Principles

Gráfépítés betöltéskorGraph construction at ingestion

A betöltéskor egy LLM entitásokat és kapcsolatokat nyer ki a szövegből, és ezekből épít fel egy strukturált tudásgráfot — a gráf csomópontjai entitások, az élei a köztük lévő relációk. At ingestion an LLM extracts entities and relationships from the text and assembles them into a structured knowledge graph — graph nodes are entities, edges are the relations between them.

Közösségek és előösszegzésCommunities and pre-summarization

A gráfot a Leiden-algoritmus közösségekbe klaszterezi, és minden közösséghez előre elkészül egy összegzés — ezekre épül a globális keresés. The graph is clustered into communities by the Leiden algorithm, and a summary is pre-computed for each community — these underpin global search.

Lokális és globális keresésLocal and global search

A lokális keresés az entitás-szomszédság bejárásával konkrét kérdésekre válaszol; a globális keresés a közösség-összegzések aggregálásával tematikus, korpusz-szintű kérdéseket szolgál ki. Local search answers specific questions by traversing the entity neighborhood; global search serves thematic, corpus-wide questions by aggregating community summaries.

Visszakeresés gráfbejárássalRetrieval as graph traversal

A visszakeresés gráfbejárás: a relációs struktúra mentén olyan összefüggéseket hoz felszínre, amelyeket a lapos vektoros keresés nem lát. Retrieval is graph traversal: following the relational structure surfaces connections that flat vector search misses.

06

Útválasztási stratégiaRouting Strategy

Egy útválasztó akkor irányítja a kérdést a Graph RAG-hez, ha az dokumentumokon átívelő, több-lépéses következtetést igényel, vagy globális, tematikus szintézist kér („Mik a fő témák…”). Az elszigetelt ténykeresést érdemes másik mintára irányítani — ott a lapos RAG olcsóbb és nem rosszabb. A router sends a query to Graph RAG when it needs multi-hop reasoning across documents, or asks for global, thematic synthesis ("what are the main themes…"). Isolated fact lookup is better routed elsewhere — there flat RAG is cheaper and no worse.

HüvelykujjszabályRule of thumb

Iparági becslés szerint kb. 1M token alatti korpusznál a gráf-indexelés többletköltsége többnyire nem éri meg — ekkor a lapos vagy hierarchikus RAG a jobb választás. A Graph RAG akkor „termeli ki” az árát, ha a kérdéshalmaz relációs vagy összegző jellegű. Industry estimates suggest that below roughly 1M tokens of corpus the graph-indexing overhead is usually not worth it — flat or hierarchical RAG is the better pick there. Graph RAG earns its cost when the query mix is relational or summarization-heavy.

Gráf-specifikus szempontGraph-specific concern

A gráf minősége implementációnként ingadozik, és közvetlenül meghatározza a visszakeresés minőségét — egy hiányos entitás-kinyerés vagy rosszul klaszterezett közösség-struktúra csendben rontja a teljes rendszert. A kiértékelésnek ezért a gráf felépítését is mérnie kell, nem csak a végső választ. Graph quality varies by implementation and directly determines retrieval quality — incomplete entity extraction or a poorly clustered community structure silently degrades the whole system. Evaluation must therefore measure the graph construction itself, not just the final answer.

KódpéldaCode example

A Microsoft GraphRAG referenciaimplementációja entitás-gráfot épít, Leiden-közösségekbe klaszterez, majd lokális vagy globális keresést futtat. A Neo4j-alapú gráf közvetlenül is lekérdezhető a neo4j-graphrag csomaggal. The Microsoft GraphRAG reference implementation builds an entity graph, clusters it into Leiden communities, then runs local or global search. A Neo4j-backed graph can also be queried directly with the neo4j-graphrag package.

graph_rag_query.py 
# pip install graphrag neo4j-graphrag
# --- Microsoft GraphRAG: local vs global search --------------------
from graphrag.query.structured_search.local_search.search import LocalSearch
from graphrag.query.structured_search.global_search.search import GlobalSearch

# Local search: entity-neighborhood traversal for a specific question
local = LocalSearch(llm=llm, context_builder=local_context, token_encoder=enc)
answer = local.search("Which filings mention executive X?")

# Global search: aggregate community summaries for a thematic query
global_search = GlobalSearch(llm=llm, context_builder=community_context, token_encoder=enc)
answer = global_search.search("What are the main risk themes across the corpus?")

# --- Neo4j-backed knowledge graph, queried directly ----------------
from neo4j_graphrag.retrievers import VectorCypherRetriever

retriever = VectorCypherRetriever(
    driver=neo4j_driver,
    index_name="entity_embeddings",
    retrieval_query="MATCH (n)-[r]->(m) RETURN n, r, m LIMIT 25",
    embedder=embedder,
)
result = retriever.search(query_text=question, top_k=5)
