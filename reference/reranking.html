01

ÁttekintésOverview

A bi-encoder embedding-alapú visszakeresés gyors, de közelítő: egyetlen vektorra tömörített dokumentumokból vektor-hasonlóság alapján keres, ezért komplex, többlépéses kérdéseknél zajosan rangsorol. A reranking egy második szakaszban cross-encoder modellt alkalmaz: ez egyszerre látja a kérdést és a dokumentumot, tokenszintű keresztfigyelemmel finomabb relevancia-pontszámot számít, majd az eredmények sorrendjét felülírja. A retrieve-then-rerank minta az iparágban bevett kétfázisú megközelítés: nagy recall az első fázisban, magas pontosság a másodikban. Bi-encoder embedding-based retrieval is fast but approximate: it searches by vector similarity over documents compressed into a single vector, so it ranks noisily on complex or multi-faceted queries. Reranking applies a cross-encoder model in a second stage: this model sees both the query and the document simultaneously, computes a finer relevance score via token-level cross-attention, and then overrides the original ranking. The retrieve-then-rerank pattern is the industry-standard two-phase approach: high recall in phase one, high precision in phase two.

A cross-encoder lassabb, mint a bi-encoder (nem lehet előre indexelni a dokumentumokat), ezért csak a visszakeresett top-N jelöltre alkalmazzák. A tipikus konfiguráció: visszakeres top-100, majd reranker top-5-öt választ ki az LLM-nek. A 2026-os reranker API-k (Cohere Rerank-4, Voyage Rerank-2, Jina Reranker v2) és open-source modellek (BGE Reranker v2.5, mxbai-rerank-large-v2) egyaránt elérhetők. A cross-encoder is slower than a bi-encoder (documents cannot be pre-indexed), so it is applied only to the top-N candidates returned by retrieval. A typical configuration: retrieve top-100, then the reranker selects the top-5 for the LLM. In 2026 both reranker APIs (Cohere Rerank-4, Voyage Rerank-2, Jina Reranker v2) and open-source models (BGE Reranker v2.5, mxbai-rerank-large-v2) are available.

Gyakorlati tanácsokPractical guidance

ErősségekStrengths

  • Jelentős pontossági javulás (15–40%) minimális architekturális változtatással: a vektoros visszakeresés megtartható.Significant precision improvement (15–40%) with minimal architectural change: the vector retrieval layer is preserved.
  • Gyengébb embedding modell kompenzálható: reranker részben pótolja az embedding hiányosságait.A weaker embedding model can be partially compensated: the reranker offsets some embedding shortcomings.
  • API-alapú rerankerek (Cohere, Voyage, Jina) azonnal integrálhatók, GPU-infrastruktúra nélkül.API-based rerankers (Cohere, Voyage, Jina) integrate immediately without GPU infrastructure.
  • Top-k csökkentésével az LLM-kontextusablak jobb kihasználtság és alacsonyabb tokenköltség érhető el.Reducing top-k improves LLM context window utilization and lowers token costs.

KompromisszumokTrade-offs

  • Késleltetési többlet: a cross-encoder N dokumentumon fut, ami 50–200 ms extra latenciát jelent tipikusan.Latency overhead: the cross-encoder runs on N documents, typically adding 50–200 ms of extra latency.
  • API-reranker esetén plusz hívási költség; open-source modellnél GPU szükséges.API rerankers incur additional call costs; open-source models require a GPU.
  • Ha az első fázis recall-ja alacsony (a releváns dokumentum nem kerül bele a top-N-be), a reranker sem tud segíteni.If first-stage recall is low (the relevant document is not in top-N), the reranker cannot help.
  • Nagyon rövid kérdéseknél (egy-két szó) a cross-encoder előnye kisebb, mint részletes kérdéseknél.For very short queries (one or two words) the cross-encoder advantage is smaller than for detailed questions.

Top-k hangolási irányelvekTop-k tuning guidelines

Visszakeresési fázis: top-50–100 a jó recall érdekében. Reranking fázis: top-5–20 a visszakapott jelöltek közül. LLM-nek adott végső kontextus: top-3–5, a kontextusablak és a válaszminőség függvényében. A reranker top-N paraméterét offline kiértékeléssel (NDCG, MRR, Recall@K) optimalizáld a saját adatkészleteden. Retrieval phase: top-50–100 for good recall. Reranking phase: top-5–20 from the returned candidates. Final context passed to the LLM: top-3–5, depending on context window size and answer quality. Optimize the reranker top-N parameter with offline evaluation (NDCG, MRR, Recall@K) on your own dataset.

KódpéldaCode example

rerank_pipeline.py 
# pip install cohere sentence-transformers
# Option A: Cohere Rerank-4 API (no GPU needed)
import cohere

co = cohere.ClientV2()

def rerank_cohere(query: str, documents: list[str], top_n: int = 5) -> list[dict]:
    response = co.rerank(
        model="rerank-v3.5",
        query=query,
        documents=documents,
        top_n=top_n,
    )
    # Each result has .index (original position) and .relevance_score
    return [
        {"doc": documents[r.index], "score": r.relevance_score}
        for r in response.results
    ]

# Option B: BGE Reranker v2.5 open-source (GPU recommended)
from sentence_transformers import CrossEncoder

reranker = CrossEncoder(
    "BAAI/bge-reranker-v2-m3",
    max_length=1024,
    device="cuda",
)

def rerank_bge(query: str, documents: list[str], top_n: int = 5) -> list[dict]:
    pairs = [[query, doc] for doc in documents]
    scores = reranker.predict(pairs)
    ranked = sorted(
        zip(documents, scores),
        key=lambda x: x[1],
        reverse=True,
    )
    return [{"doc": doc, "score": float(score)} for doc, score in ranked[:top_n]]

# Full retrieve-then-rerank pipeline example
def rag_with_reranking(query: str, vector_store, llm) -> str:
    # Stage 1: fast approximate retrieval (bi-encoder)
    candidates = vector_store.similarity_search(query, k=50)
    candidate_texts = [c.page_content for c in candidates]

    # Stage 2: precise reranking (cross-encoder)
    reranked = rerank_cohere(query, candidate_texts, top_n=5)
    context = "\n\n".join(r["doc"] for r in reranked)

    # Stage 3: generation
    return llm.invoke(f"Context:\n{context}\n\nQuestion: {query}")
