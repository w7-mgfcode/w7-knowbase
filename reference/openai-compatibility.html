01

ÁttekintésOverview

Az OpenAI API két, egymás mellett élő szöveges végpontcsaládot kínál. A Chat Completions API (POST /v1/chat/completions) a klasszikus, állapotmentes végpont: minden kérésben el kell küldeni a teljes üzenet-előzményt. Nincs megszüntetési dátuma — teljes körűen támogatott, és ez adja a legnagyobb hordozhatóságot a nem OpenAI, OpenAI-kompatibilis szerverek felé. A Responses API (POST /v1/responses) az újabb, állapottartó szuperhalmaz, amely a beépített eszközöket és az MCP-t is kiszolgálja; új projektekhez ezt ajánlják. The OpenAI API offers two coexisting text endpoint families. The Chat Completions API (POST /v1/chat/completions) is the classic, stateless endpoint: every request must carry the full message history. It has no deprecation date — fully supported, and it gives the most portability toward non-OpenAI, OpenAI-compatible servers. The Responses API (POST /v1/responses) is the newer, stateful superset that also hosts the built-in tools and MCP; it is the recommendation for new projects.

A Responses API mellé az OpenAI két új társvégpontot is bevezetett: a Conversations API-t (állapottartó beszélgetésszálak, az Assistants-szálak utódja) és egy /compact végpontot a kontextus tömörítéséhez. A választás nem kötelező: a Chat Completions hosszú távon is marad. A Responses API viszont érvelő modelleknél kb. +3%-os SWE-bench eredményt és 40–80%-kal jobb prompt-gyorsítótár-kihasználtságot hoz. Ez az oldal mindkét felületet végigveszi, majd kitér a tágabb OpenAI-kompatibilis ökoszisztémára is. Alongside the Responses API, OpenAI also introduced two companion endpoints: the Conversations API (stateful conversation threads, the successor to Assistants threads) and a /compact endpoint for context compaction. The choice is not mandatory: Chat Completions stays for the long run. The Responses API, however, delivers roughly +3% on SWE-bench with reasoning models and 40–80% better prompt-cache utilization. This page walks through both interfaces, then covers the broader OpenAI-compatible ecosystem.

Végpontok és hitelesítésEndpoints & Authentication

Az API REST-alapú, HTTPS-en, JSON kérés- és válasz-törzzsel. A két szöveges végpont ugyanazt a hitelesítést használja; a különbség az állapotkezelésben és a beépített képességekben van. The API is REST-based over HTTPS, with JSON request and response bodies. The two text endpoints share the same authentication; the difference is in state handling and built-in capabilities.

HitelesítésAuthentication

Minden kérés egy Authorization: Bearer <kulcs> fejlécet igényel. A modern kulcsok projekt-hatókörűek (sk-proj- előtag); opcionálisan az OpenAI-Organization és OpenAI-Project fejlécekkel szűkíthető a hatókör. A kulcs sosem kerül kliensoldali kódba — környezeti változó a fejlesztéshez, titokkezelő (secret manager) az éles környezethez. Every request requires an Authorization: Bearer <key> header. Modern keys are project-scoped (the sk-proj- prefix); the optional OpenAI-Organization and OpenAI-Project headers narrow the scope further. The key never goes into client-side code — an environment variable for development, a secret manager for production.

Fontos változásokImportant changes

A 2026-02-13-i visszavonás csak a ChatGPT-et érintette: a GPT-4o és a GPT-4.1 továbbra is hívható az API-ból — az OpenAI megfogalmazásában „az API-ban egyelőre nincs változás”. Az Assistants API elavult (2025-08-26), végleges megszűnése 2026-08-26 — a migráció a Responses API + Conversations API felé vezet. Az o4-mini API-elérése 2026-10-23-án szűnik meg. The 2026-02-13 retirement affected ChatGPT only: GPT-4o and GPT-4.1 remain callable from the API — in OpenAI's wording, "in the API, there are no changes at this time." The Assistants API is deprecated (2025-08-26), with sunset on 2026-08-26 — migration goes to the Responses API + Conversations API. The o4-mini API access is shut down on 2026-10-23.

Streaming és SSEStreaming & SSE

A streaming a választ tokenekre bontva, valós időben adja vissza — a felhasználó az első tokent töredék idő alatt látja. A két végpont eltérő folyamformátumot használ. Streaming returns the response in real time, broken into tokens — the user sees the first token in a fraction of the time. The two endpoints use different stream formats.

Chat Completions
SSE adatfolyamSSE stream

A stream: true hatására Server-Sent Events érkezik: minden esemény egy data: sorral kezdődik, és egy chat.completion.chunk objektumot szállít. With stream: true, Server-Sent Events arrive: every event begins with a data: line and carries a chat.completion.chunk object.

  • Minden chunk egy choices[].delta töredék.Each chunk is a choices[].delta fragment.
  • Lezárás: a literál data: [DONE] sor.Termination: the literal data: [DONE] line.
  • stream_options: {"include_usage": true} → záró, csak token-felhasználást tartalmazó chunk.stream_options: {"include_usage": true} → a final usage-only chunk.
Responses API
Típusos eseményekTyped events

A Responses API szemantikus, típusos eseményeket küld — nincs [DONE]. Minden eseménynek van sequence_number-e. The Responses API emits semantic, typed events — there is no [DONE]. Every event has a sequence_number.

  • response.created — a folyam kezdete.response.created — the start of the stream.
  • response.output_text.delta — szövegtöredékek; response.function_call_arguments.delta — eszközargumentumok.response.output_text.delta — text fragments; response.function_call_arguments.delta — tool arguments.
  • response.completed — záró esemény, benne a teljes response és usage.response.completed — the terminal event, embedding the final response and usage.

Streaming tippStreaming tip

Streameléskor a hibakezelés nehezebb: a HTTP-státusz már a hibatartalom előtt megérkezik, így a folyam közben fellépő hibát is kezelni kell. A Responses API error eseménye, illetve a Chat Completions csonka (a [DONE] nélkül záruló) folyama jelzi a megszakadást — a kliensnek mindkettőre fel kell készülnie. Error handling is harder when streaming: the HTTP status arrives before the error body, so failures mid-stream must also be handled. The Responses API error event, and a truncated Chat Completions stream (one ending without [DONE]), both signal a break — the client must be ready for either.

Function calling és eszközökFunction calling & tools

A function calling során a modell strukturált JSON-t állít elő egy általunk leírt függvény meghívásához. A futtatást a saját kódunk végzi; az eredményt visszaadva a modell befejezi a választ. strict mód és tool_choicestrict mode & tool_choice

A strict: true a függvény-sémát a dekódolási rétegen kényszeríti ki. A tool_choice szabályozza a hívást: auto (alapértelmezett), required, none, egy megnevezett függvény vagy allowed_tools. A parallel_tool_calls alapból igaz — de párhuzamos hívásoknál a strict séma-betartás nem garantált. A válaszalak eltér: a Chat Completions a message.tool_calls[]-ot adja, a Responses API az output[] tömbben type: "function_call" elemeket call_id-vel — az arguments mindig JSON-kódolt string. 2026-os újdonság a Tool Search (gpt-5.4+, lusta eszközbetöltés) és a kontextusmentes nyelvtannal definiált egyéni eszközök. strict: true enforces the function schema at the decoding layer. tool_choice governs the call: auto (default), required, none, a named function, or allowed_tools. parallel_tool_calls defaults to true — but with parallel calls strict schema enforcement is not guaranteed. The response shape differs: Chat Completions returns message.tool_calls[], the Responses API returns type: "function_call" items with a call_id in the output[] array — and arguments is always a JSON-encoded string. New in 2026: Tool Search (gpt-5.4+, lazy tool loading) and custom tools defined with context-free grammars.

Strukturált kimenetekStructured Outputs

A strukturált kimenet garantálja, hogy a modell válasza egy megadott JSON-sémát követ. Ez a régi JSON mode utódja — és élesben az alapértelmezett választás. Structured Outputs guarantees that the model's response follows a supplied JSON schema. It is the successor to the legacy JSON mode — and the production default.

SémaszabályokSchema rules

A kérésben: response_format: {type: "json_schema", json_schema: {name, strict: true, schema}}. strict: true esetén minden objektumon kötelező az additionalProperties: false, és minden mezőnek szerepelnie kell a required tömbben — az „opcionális” mezőt nullable unióként kell modellezni. Így a kötelező mezők nem maradhatnak ki és az enumok nem sérülhetnek; a modell elutasítását külön refusal mező jelzi. In the request: response_format: {type: "json_schema", json_schema: {name, strict: true, schema}}. With strict: true, every object must carry additionalProperties: false, and every field must appear in required — model an "optional" field as a nullable union. This way required fields cannot be omitted and enums cannot be violated; a model refusal surfaces in a distinct refusal field.

Beépített eszközök és MCPBuilt-in tools & MCP

A Responses API beépített (hosztolt) eszközöket tesz ugyanabba a tools tömbbe, mint a saját függvényeinket. Egy részük token-en felüli díjat is felszámol. The Responses API places built-in (hosted) tools into the same tools array as our own functions. Some of them also carry billing beyond tokens.

Web SearchWeb Search

{type: "web_search"} — a modell élő webes keresést futtat, és a találatokat a válaszba építi. {type: "web_search"} — the model runs a live web search and grounds the answer in the results.

File SearchFile Search

{type: "file_search", vector_store_ids: [...]} — hosztolt vektortárból keres (kezelt RAG). {type: "file_search", vector_store_ids: [...]} — searches a hosted vector store (managed RAG).

Code InterpreterCode Interpreter

{type: "code_interpreter"} — sandboxban Python-kódot futtat számoláshoz, adatfeldolgozáshoz. {type: "code_interpreter"} — runs Python in a sandbox for computation and data work.

Computer UseComputer Use

A modell egy virtuális gépet vezérel — kattint, gépel, navigál — felhasználói felületeken. The model drives a virtual machine — clicking, typing, navigating — across user interfaces.

Image GenerationImage Generation

A modell képet állít elő a válasz részeként, külön képgeneráló hívás nélkül. The model produces an image as part of the response, with no separate image call.

MCP-eszközökMCP tools

Az MCP-eszköz — {type: "mcp", server_label, server_url, require_approval} — egy távoli MCP-szerver eszközeit importálja az API-ba; egy mcp_list_tools kimeneti elem sorolja fel őket. Ugyanez a mechanizmus hajtja az OpenAI Connectorokat. A jóváhagyás alapból kért. The MCP tool — {type: "mcp", server_label, server_url, require_approval} — imports a remote MCP server's tools into the API; an mcp_list_tools output item lists them. The same mechanism powers OpenAI Connectors. Approval is requested by default.

OpenAI-kompatibilis ökoszisztémaOpenAI-compatible ecosystem

Az „OpenAI-kompatibilis” egy olyan szervert jelent, amely az OpenAI kérés/válasz sémáját és URL-útvonalait (főleg a POST /v1/chat/completions-t) tükrözi — így bármely OpenAI SDK működik vele, ha csak a base_url-t és az api_key-t cseréljük. "OpenAI-compatible" means a server that mirrors OpenAI's request/response schema and URL paths (chiefly POST /v1/chat/completions) — so any OpenAI SDK works with it by changing only base_url and api_key.

Kompatibilis ≠ azonosCompatible ≠ identical

A legtöbb szerver csak a Chat Completionst valósítja meg (a Responses API-t nem); a function calling / tool_choice / strukturált kimenet támogatása szerverenként eltér; a streaming chunk-formátum és a [DONE] kezelése különbözik; a /v1/embeddings nem univerzális; a nem támogatott paramétereket a szerverek gyakran csendben eldobják; a Batch, a prompt-gyorsítótár és a finomhangolás többnyire hiányzik. A helyi szerverek bármilyen nem üres kulcs-stringet elfogadnak; a LiteLLM proxy a kivétel — a csupasz gyökérre kell mutatni, /v1 nélkül. Most servers implement only Chat Completions (not the Responses API); function calling / tool_choice / structured-output support varies per server; the streaming chunk shape and [DONE] handling differ; /v1/embeddings is not universal; unsupported parameters are often silently dropped; Batch, prompt caching and fine-tuning are usually absent. Local servers accept any non-empty key string; the LiteLLM proxy is the exception — point at the bare root, with no /v1.

Ajánlott gyakorlatokBest practices

  • Új projekthez a Responses API-t válaszd — beépített eszközök, jobb gyorsítótár.Choose the Responses API for new projects — built-in tools, better caching.
  • Mindig állíts kimeneti felső korlátot (max_output_tokens / max_completion_tokens).Always set an output cap (max_output_tokens / max_completion_tokens).
  • Token-számláláshoz tiktoken, o200k_base kódolással.Count tokens with tiktoken using the o200k_base encoding.
  • 429 és 5xx hibáknál exponenciális backoff + jitter, a Retry-After fejléc figyelembevételével.On 429 and 5xx errors use exponential backoff + jitter, honoring the Retry-After header.
  • Function callingnál strict: true séma.Use a strict: true schema for function calling.
  • A statikus tartalmat (system üzenet, eszköz-definíciók) tartsd a prompt elején — a gyorsítótár prefix-egyezésre épül.Keep static content (system message, tool defs) at the front of the prompt — caching matches on the prefix.
  • API-kulcs környezeti változóban (fejlesztés), titokkezelőben (éles).Keep the API key in an environment variable (dev), in a secret manager (prod).

Gyakori hibákCommon pitfalls

  • API-kulcs beégetése forráskódba vagy kliensoldali kódba.Hardcoding the API key in source or in client-side code.
  • Abból kiindulni, hogy a GPT-4o eltűnt az API-ból — csak a ChatGPT-ből vonult vissza.Assuming GPT-4o is gone from the API — it was only retired from ChatGPT.
  • Új projektet az Assistants API-ra építeni (2026-08-26-án megszűnik).Building a new project on the Assistants API (it sunsets 2026-08-26).
  • Hosszú kimenetet streaming nélkül kérni.Requesting long output without streaming.
  • Hiányzó 429 / 5xx hibakezelés és újrapróbálkozási logika.Missing 429 / 5xx error handling and retry logic.

Token és költségToken & cost

Token-számlálás tiktoken + o200k_base. A kimeneti korlát paramétere eltér: max_tokens (régi CC), max_completion_tokens (CC érvelő modellek), max_output_tokens (Responses API). A gyorsítótárazott input kb. 90%-kal, a Batch API kb. 50%-kal olcsóbb. Count tokens with tiktoken + o200k_base. The output-cap parameter differs: max_tokens (legacy CC), max_completion_tokens (CC reasoning models), max_output_tokens (Responses API). Cached input is ~90% cheaper, the Batch API ~50% cheaper.

BiztonságSecurity

Soha ne égess be kulcsot, és ne küldd kliensre. Fejlesztéshez környezeti változó, éleshez titokkezelő. Projekt-hatókörű kulcsot használj, 60–90 naponta rotálva. A kulcsot sose logold. Never hardcode a key, never ship it to the client. An environment variable for dev, a secret manager for prod. Use a project-scoped key, rotated every 60–90 days. Never log the key.

KódpéldaCode example

Ugyanaz az SDK kiszolgálja a Chat Completionst, a Responses API-t és bármely OpenAI-kompatibilis szervert — csak a base_url és az api_key változik. The same SDK serves Chat Completions, the Responses API and any OpenAI-compatible server — only base_url and api_key change.

openai_quickstart.py 
# pip install openai
from openai import OpenAI

client = OpenAI()  # reads OPENAI_API_KEY from the environment

# --- Chat Completions: stateless, maximum portability ---------------
chat = client.chat.completions.create(
    model="gpt-5.5",
    messages=[
        {"role": "system", "content": "You are a concise assistant."},
        {"role": "user", "content": "Explain RAG in one sentence."},
    ],
    max_completion_tokens=200,
)
print(chat.choices[0].message.content)

# --- Responses API: stateful, with a built-in tool -----------------
resp = client.responses.create(
    model="gpt-5.5",
    input="Summarize today's AI news.",
    tools=[{"type": "web_search"}],
    store=True,                       # keep context server-side
)
print(resp.output_text)

# --- Same SDK, an OpenAI-compatible server (vLLM) -------------------
# Only base_url + api_key change; local servers accept any key string.
local = OpenAI(base_url="http://localhost:8000/v1", api_key="token-abc123")
vllm = local.chat.completions.create(
    model="meta-llama/Llama-3.3-70B-Instruct",
    messages=[{"role": "user", "content": "Hello from vLLM!"}],
)
print(vllm.choices[0].message.content)
